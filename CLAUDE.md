# InterviewNotes

Personal interview-preparation notes, built with Docusaurus and deployed to GitHub Pages
(`https://maindolaamit.github.io/interview-notes/`).

## Commands

- `npm run dev` — local dev server on port 3005
- `npm run build` — production build; must pass before committing (`onBrokenLinks: 'throw'` catches broken links)
- `npm run serve` — serve the production build locally

Deployment: merging a PR into `main` deploys the site (`.github/workflows/deploy.yml`); `ci.yml` checks every PR into `main`.
Branch from the latest `main`, and don't stack branches: PRs are squash-merged, so a branch built on another unmerged branch will conflict.

If `artifactory.nordstrom.com` is unreachable, install from the public registry for that command only:
`npm ci --registry=https://registry.npmjs.org/`. Don't edit `~/.npmrc`. Lockfile URLs must stay on `registry.npmjs.org`.

## Where notes go

Each top-level folder in `docs/` is one section with its own autogenerated sidebar (`sidebars.ts`). In the navbar,
Languages & Frameworks and Programming are grouped under a "Coding" dropdown, and Architecture and System Design under "Design".
For a new note, ask these questions in order — the first "yes" decides:

| # | Question | Section | Folder |
|---|----------|---------|--------|
| 1 | About one language's syntax, runtime, or framework API? | Languages & Frameworks | `docs/languages/` |
| 2 | About LLMs / AI concepts? | GenAI | `docs/genai/` |
| 3 | About a specific product or tool you deploy/operate (Kafka, Kubernetes, AWS, Docker, Redis, CI/CD)? | Platform | `docs/platform/` |
| 4 | A tool-agnostic pattern for how services are structured or communicate? | Architecture | `docs/architecture/` |
| 5 | About writing code inside one service (DSA, OOP, SOLID, design patterns, LLD, TDD, clean code)? | Programming | `docs/programming/` |
| 6 | Designing an entire system end to end ("Design X"), including HLD? | System Design | `docs/designs/` |
| 7 | Soft skills / how to answer? | Behavioural | `docs/behavioural/` |

When a topic spans sections, put the concept and the tool in separate places and cross-link them:
- Messaging concepts (queues vs. topics, delivery guarantees, outbox) → `architecture/microservices/messaging-brokers.mdx`;
  Kafka internals → `platform/kafka/`.
- Deploying microservices in general → `architecture/microservices/deployment.mdx`; Kubernetes objects → `platform/kubernetes/`.
- GenAI concepts → `genai/`; "Design a RAG chatbot" style problems → `designs/interviews/`.

## Conventions

- Folder and file names: lowercase kebab-case, no numeric prefixes. Set order with `sidebar_position` in front matter,
  or `_category_.json` for folders without an `index.mdx`.
- A topic that will grow gets its own folder with an `index.mdx`; a small topic can be a single `.mdx` file.
- Keep images next to the page that uses them (in the same folder or an `img/` subfolder) and link them relatively.
- Link to other docs with absolute doc paths without the file extension, e.g. `/docs/platform/kafka`.
- When you move or rename a doc, add a redirect for the old URL in the `@docusaurus/plugin-client-redirects` config
  in `docusaurus.config.ts`. Skip redirects for case-only renames: on case-insensitive filesystems the redirect would overwrite the page.
- Run `npm run build` after any move or rename.

## Page template

```mdx
---
title: Topic Name
description: "Topic Name Interview Questions"
sidebar_position: 1
---

Short overview: what this is and when it is used. Link related notes in other sections.

## Key concepts
Core ideas, with diagrams (Mermaid is enabled) where they help.

## Interview questions
### Question?
Concise answer first, then detail, trade-offs, and a code example if relevant.

## References
- Links to sources
```

## Page format: summary first, depth on demand

Pages should be quick to skim. Detail goes behind expandable sections or tabs (see `docs/platform/kafka/` for examples).

- Start with a `:::tip Key takeaways` box of 3–5 bullets.
- Under each H2, give a short visible summary (a paragraph or a table). Put code, diagrams and long explanations in `<details><summary>…</summary>`, with blank lines around the markdown inside.
- Use `<Tabs>`/`<TabItem>` for parallel alternatives: configs (yml / gradle), options (blocking vs. non-blocking), or pros vs. cons.
- Use `:::warning` / `:::danger` for traps and incidents.
- Section index pages (`index.mdx`) end with `<DocCardList />`.
- Interview questions: one `<details>` per question, with the summary `**Qn · tag.** question`. Put the options in the body, then a nested `<details><summary>Show answer</summary>` containing a `:::tip Answer: X` box and the explanation. Group questions by level with Tabs.
- Diagrams are SVGs in an `img/` folder next to the page. Give them a white background and explicit width and height, and escape `&` as `&amp;`.
- This repo is public. Don't include employer-specific names, namespaces or internal tools; keep examples generic.
